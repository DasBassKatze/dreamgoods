# DreamGoods — генерация карточек товаров с ИИ-контролем

## Установка и запуск (Windows)
1. Установите Python 3.11+ и Docker Desktop.
2. `Установка.bat` — поставит библиотеки Python и создаст `.env`.
3. Запустите Docker Desktop (в нём работает только PostgreSQL), затем `Запуск DreamGoods.bat`.
   Откроется http://127.0.0.1:8765. Миграции базы применяются при запуске автоматически.

Интерфейс в архиве уже собран (папка `dreamgoods/web`), Node.js для работы **не нужен**.
Он нужен, только если вы меняете код интерфейса (`frontend/`) — тогда `Сборка интерфейса.bat`.

## Структура проекта
```
run_dreamgoods.py      запуск: проверка базы → миграции → хранилище → очередь → веб-сервер
dreamgoods/                бэкенд (Python, FastAPI)
  api/                 HTTP-слой
    app.py             приложение: обработка ошибок, раздача собранного интерфейса
    routers/           маршруты по разделам: projects, settings, generation, frames, products, imports, media
    schemas.py         схемы запросов (Pydantic) — проверка входных данных
    deps.py            общие зависимости: проект из пути, проверка ключа
  services/            бизнес-логика: projects, board (состояние экрана), metrics, frames, products,
                       importer, export, legacy (перенос старой версии), common (общее с воркерами)
  workers/             фоновые задания: queue (очередь в PostgreSQL), generate, check, profile, refs
  ai/                  модели: polza (API), prompts (профиль → промпты), qc (проверка), views (ракурсы), images
  db/                  engine.py (подключение), models.py (таблицы SQLAlchemy)
  core/                config (.env), logs, settings (настройки по умолчанию), storage (файлы), events (лента)
  web/                 собранный интерфейс (генерируется, руками не править)
migrations/            миграции схемы (Alembic)
frontend/              интерфейс: React + TypeScript + Vite
  src/api/             клиент API и типы ответов
  src/components/      шапка, панель, карточка товара, плитка кадра, метрики, журнал, окна, уведомления
  src/features/        крупные окна: просмотр кадра, настройки, каталог моделей, профиль товара, импорт
  src/hooks/           опрос состояния проекта, действия запуска, запоминание в браузере
```
Зависимости слоёв идут сверху вниз: `api → services → workers → ai → db/core`.

## Пресеты генерации (кнопка «🎛 Пресет» в шапке)
Пресет = уровень качества (Черновик / Стандарт / Премиум / Свой) + план кадров на товар по блокам: на белом фоне,
детали крупно, на человеке крупно, в полный рост, лайфстайл без людей. Пресеты общие для организации; один — пресет
проекта, у товара может быть свой. «Применить к товарам» — выбранным, по категориям или всем: промпты пересобираются
сразу, если в профиле хватает кадров нужных видов, иначе ИИ заново составляет профиль. Кадры вне нового плана скрываются,
их история сохраняется.
В пресете также: **площадка** (Wildberries / Ozon / Яндекс Маркет / своя) — формат кадра, минимальный размер и правила
главного фото: первый кадр «на белом фоне» становится обложкой по правилам площадки; **строгость проверки** — строго /
обычно / только критичное. Применять пресет можно по категориям и **подразделам** (Сапоги, Ботинки…): подраздел ИИ пишет
в профиль товара, для старых профилей — кнопка «Определить подразделы ИИ».

## Ручной режим плана и модели по блокам
В пресете план кадров бывает **авто** (кол-во по блокам, кадры придумывает ИИ) или **ручной** — свои методы съёмки:
название, промпт (можно по-русски, `{товар}` подставится), тип кадра, количество, своя модель. Описание товара, правила
сторон, анатомию и обложку площадки код добавляет сам. **Модель генерации на блок**: белый фон и детали — дешёвой моделью,
кадры с человеком — сильной; рядом статистика по вашим кадрам (% с 1-й попытки и цена) для выбора.

## Референсы оформления (кнопка «🎨 Оформление» в шапке)
1–3 фото-примера стиля + коротко, что взять («тёплый вечерний свет, бежевая гамма, фон не брать»). ИИ разбирает стиль
(свет, цвет, фон, композиция, настроение, обработка), фото идут генератору как пример оформления — без копирования
предметов, людей и текста — только для отмеченных видов кадров; обложка карточки остаётся по правилам площадки.
Референс — у клиента; выбирается для проекта и при необходимости свой для товара (в профиле товара).

## Модели клиента (кнопка «👤 Модель» в шапке)
Человек, который «носит» товары на кадрах в использовании и общих планах. Модель принадлежит клиенту и доступна во всех его проектах.
- **Свои фото**: 1–4 фото (лицо и в полный рост) + согласие человека → ИИ описывает внешность.
- **Сгенерировать образ**: пожелания по-русски (можно стиль: готика, стритвир…) → ИИ пишет для каждого варианта «паспорт образа»
  (внешность + макияж, укладка, стиль одежды, аксессуары, подача) → 1–4 варианта → выбираете один (его паспорт сохраняется) →
  по желанию «ракурсы» (портрет, ¾, профиль). «Изменить внешность» — правка выбранной модели по запросу («рыжие волосы»).
  Паспорт виден и редактируется в карточке модели; на кадрах товара он задаёт макияж, укладку и стиль одежды.
- **Для каких товаров**: в карточке модели отмечаются категории и подразделы («Обувь», «Обувь / Ботфорты») — эти товары,
  включая новые, снимаются на ней. Порядок: модель в профиле товара → по подразделу → по категории → модель проекта.
- Модель проекта задаётся в окне моделей, своя у товара — в профиле товара. При генерации кадров с человеком фото модели
  идут генератору после фото товара (настройка «Фото модели клиента»), кадры на белом фоне делаются без модели.

## Правка готового фото
В окне кадра вместо промпта — блок «✏️ Правка фото»: напишите своими словами, что изменить («убери складку на заднике,
фон чуть теплее»). Генератор получает текущую версию кадра и фото товара и меняет только указанное; результат проходит
ИИ-проверку. Все версии кадра видны под картинкой — любую можно открыть, вернуть («Сделать основной») или править дальше.

## Сайт: вход, личные кабинеты, мастер-аккаунт
Вход по логину и паролю (сессия в cookie на 30 дней). Регистрации нет — учётные записи заводит мастер.
- **Мастер-аккаунт** (первый создаётся из `.env`: `DREAMGOODS_ADMIN_EMAIL` / `DREAMGOODS_ADMIN_PASSWORD`) видит все кабинеты
  и раздел «Управление сервисом»: пользователи, финансы, ключи Polza, аналитика, журнал сервера, технические настройки.
- **Пользователь** работает в своём кабинете: свои проекты, товары, модели, оформление, свои пресеты (+ общие пресеты мастера),
  баланс и история списаний. Чужие проекты и файлы ему недоступны ни в интерфейсе, ни через API.
- **Баланс**: каждая платная операция списывается сразу — себестоимость Polza × наценка (общая или своя у пользователя).
  При нуле новые задания не запускаются. Пополняет мастер («Пользователи» → «Пополнить»).
- **Ключи Polza**: несколько ключей; ключ можно закрепить за пользователем, остальные пользователи распределяются по общему пулу
  (у каждого всегда один и тот же ключ). Без ключей — ключ из технических настроек, как раньше.
- Очередь честная: у кого сейчас меньше запущенных заданий, тот получает поток первым.

## Связь с Polza
Общий пул соединений с автоповторами там, где это безопасно (обрыв при опросе статуса и скачивании, «Polza занята»,
запрос не дошёл). Номер задачи Polza сохраняется в базу сразу после отправки: если связь пропала, ожидание затянулось
или сервер перезапустили, оплаченный результат дозагружается автоматически (раз в минуту) — без повторной оплаты.
Сколько генераций идёт одновременно, меняется в админ-панели.

## API
Документация со всеми методами и схемами: http://127.0.0.1:8765/docs.
Все методы проекта — под `/api/projects/{id}/…`, товары и кадры адресуются по id
(`/frames/{frame_id}/review`, `/products/{product_id}/profile`), файлы — `/api/assets/{uuid}?w=ширина`.

## Данные
- **PostgreSQL** — организация → клиенты → проекты → товары, фото (с ракурсами), профили (с версиями), кадры,
  каждая генерация, проверки ИИ, ручная разметка, очередь заданий, журнал расходов, импорт.
- **Файлы** — папка `data/files` или облачный S3, переключается в `.env` (STORAGE).
  Ключ файла = хэш содержимого, одинаковые файлы хранятся один раз. Перенос в облако: `python run_dreamgoods.py --upload-to-s3`.
- **Очередь** в PostgreSQL: задания переживают перезапуск; прерванные сбоем генерации не повторяются
  автоматически (защита от двойной оплаты).

## Переход со старого названия (studio → dreamgoods)
База осталась прежней: том Docker `studio_pgdata`, пользователь и база `studio` — это внутренние имена, менять их не нужно.
`Запуск DreamGoods.bat` сам останавливает старый контейнер `studio-postgres-1`. Старый `.env` подходит как есть.

## Полезное
- Резервная копия файлов: скопируйте папку `data/files`.
- Резервная копия базы: `docker compose exec postgres pg_dump -U studio studio > backup.sql`.
- Лог: `logs/dreamgoods.log`; подробно в консоли — `Запуск DreamGoods (подробный лог).bat`.
- Перенос данных старой версии вручную: `python run_dreamgoods.py --import-legacy "D:\путь\к\ShoesEdit"`.



## Тестовая ветка Dev-GPT

Изменения: резерв на каждый платный запрос, однократное списание, бюджеты запуска и автоматических переделок,
ограничение потоков клиента, атомарная очередь, строгие ответы QC и тяжесть дефектов, массовая приёмка,
сравнение оригиналов и версий, серверная пагинация и SSE, смета, экспорт по пресету и резервное копирование.

### Отдельный тестовый запуск Windows

1. Получите ветку `Dev-GPT` в отдельную папку. Установите зависимости `python -m pip install -r requirements.txt`.
2. Создайте `.env` из `.env.example`. Для локального запуска пароль задавать необязательно:
   если `DREAMGOODS_ADMIN_PASSWORD` не задан или пустой, первый мастер создаётся с паролем `admin`
   (логин по умолчанию тоже `admin`). Существующие учётные записи не меняются.
3. Запустите Docker Desktop, затем `Запуск Dev-GPT.bat`.
4. Тестовый интерфейс: http://127.0.0.1:8766. Отдельные PostgreSQL (порт 5433, том `dreamgoods_dev_gpt_pgdata`),
   файлы, журнал и резервные копии. Старые данные автоматически не импортируются.
5. Создайте клиента, пополните баланс, задайте Polza-ключ и загрузите небольшой набор фото.

Миграция `0013` применяется при старте. На действующей базе перед миграцией остановите все старые воркеры
и сделайте копию: старый код не должен работать одновременно с новой схемой и биллингом.

### Деньги и очередь

В разделе мастера **Сверка платежей** задаются минимальные резервы на запрос (себестоимость: 50 ₽ за изображение,
5 ₽ за чат по умолчанию) и лимит потоков клиента (по умолчанию 2). Резерв выбирается как максимум минимального резерва
и максимальной стоимости последних 100 вызовов той же модели/типа × 1,25, затем применяется наценка клиента.
Недостаточно доступных средств — новый запрос не отправляется. После ответа резерв заменяется фактическим списанием.

Бюджет запуска включает проверки и переделки; бюджет переделок — его часть. Перед каждым следующим вызовом
сравниваются фактические расходы и резервы. **Оценка не является фиксированным тарифом:** если провайдер выставит цену
выше резерва, уже оплаченная операция учитывается полностью и может превысить бюджет или баланс. Новые запросы
будут заблокированы. Установите резервы с запасом для используемых моделей. Смета показывает историю по модели,
блоку и категории либо явно обозначенный резервный расчёт при отсутствии истории.

При неоднозначном обрыве резерв сохраняется, платный POST не повторяется вслепую. Известные задачи кадров
дозагружаются через прежний механизм. Операции без номера задачи сверяются мастером с журналом провайдера;
для потерянных задач с номером ручная сверка разрешена через сутки. Стоимость 0 означает подтверждённое отсутствие
списания. Ввод стоимости и основание сверки попадают в журнал. Не освобождайте резерв только по факту таймаута.

### Приёмка и каталог

**Приёмка кадров**: отдельная постраничная очередь, фильтры статуса/категории дефекта, исходник и результат рядом,
сравнение с историей версий, масштаб и синхронная прокрутка, групповые решения и правки. Клавиши 1/2 — принять/отклонить,
стрелки — кадры. Перед действием проверяется версия: устаревшее решение не применяется к новому изображению.
Старые QC-записи без структурированной категории доступны через «Все причины».

Каталог возвращает 40 товаров на страницу, максимум API — 100. Поиск/фильтры выполняются на сервере,
глобальные счётчики не зависят от страницы. «Выбрать страницу» выбирает только загруженные товары.
SSE передаёт уведомление об изменении, полное состояние запрашивается только для видимой страницы.
Резервное обновление раз в 30 секунд покрывает прокси без SSE и изменения вне очереди. Для reverse proxy отключите
буферизацию на `/api/projects/*/events`; авторизация и доступ проверяются в течение открытого потока.

### Экспорт и QC

Экспорт: оригиналы или JPEG/PNG с пропорциями и минимальным размером из действующего пресета товара,
без обрезки товара (белые поля). Можно выдавать только полные принятые комплекты.
`manifest.json` содержит порядок, обложку и предупреждения об исходниках малого размера.
Правила берутся из конфигурации проекта, а не обновляются с сайтов маркетплейсов автоматически.

`python scripts/qc_benchmark.py export benchmark.json` выгружает последние ручные решения как эталон.
`python scripts/qc_benchmark.py evaluate benchmark.json predictions.json` сравнивает новые результаты и считает
пропуски брака/ложные отказы. Формат predictions: `[{"generation_id":123,"pass":true}]`.
Отложите часть примеров для проверки, не подбирайте промпты на всём эталоне. Скрипт сам платные запросы не запускает.

### Резервные копии

Установите PostgreSQL client tools (`pg_dump`, `pg_restore`) в PATH или задайте `DREAMGOODS_PG_BIN`.
При запущенном сервере копия создаётся автоматически раз в 24 часа, хранится 7 копий.
Параметры `.env`: `DREAMGOODS_BACKUP_HOURS` (0 — отключить), `DREAMGOODS_BACKUP_KEEP`, `DREAMGOODS_BACKUP_DIR`,
`DREAMGOODS_BACKUP_VERIFY_RESTORE` (по умолчанию true).
В копию входят дамп БД, файлы из local/S3 и SHA-256. Рабочие секреты `.env` в копию не включаются.
Проверка восстановления создаёт временную БД `dg_verify_*`, восстанавливает её, проверяет ссылки на файлы
и удаляет временную БД; пользователю PostgreSQL нужно право CREATEDB. Рабочая БД не заменяется.

Вручную: `python scripts/backup.py`; проверить существующую копию: `python scripts/backup.py --verify-only backups/ИМЯ`.
`--no-restore-test` оставляет проверку контрольных сумм и структуры дампа, без пробного восстановления.
Ошибки автоматического копирования видны в журнале сервера. Отдельно храните копии вне сервера и секреты для запуска.

### Проверки

`python -m pip install -r requirements-dev.txt` → `python -m pytest -q`.
Без `TEST_DATABASE_URL` быстрые тесты используют временную SQLite; конкурентные тесты пропускаются.
Для полноценной проверки укажите URL **отдельной одноразовой PostgreSQL** в `TEST_DATABASE_URL`:
тесты очищают её таблицы. GitHub Actions для Dev-GPT поднимает PostgreSQL 16, проверяет миграцию вверх/вниз,
конкурентные списания, очередь и сборку интерфейса. Настоящие платные генерации в тестах не вызываются.
